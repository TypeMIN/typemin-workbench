## 2. 설계 원칙

1. **엔진 순수성 유지.** 접속·제한시간·리액션·사운드는 방(room) 계층의 관심사이며 `GameState`와 `transition()`에 넣지 않는다. 엔진 변경은 카드 카운팅에 필요한 공개 정보 추가로 한정한다.
2. **서버 권위.** 제한시간 만료 판정과 자동 행동은 서버가 수행하고 행동 로그에 일반 행동과 같은 형식으로 남긴다. 클라이언트 타이머는 표시용이다.
3. **정보 은닉 경계 유지.** 상대 손패, 덱 순서, RNG, 투수의 비공개 선택은 여전히 `getGameView()`를 통과하지 않는다.
4. **카드 창 신호는 의도된 공개 정보로 승격.** "상대에게 지금 낼 수 있는 카드가 있다"는 사실과 그 뒤 사용/패스 여부를 숨기지 않고, 오히려 기록·표시해 상대 손패를 추리(카운팅)하는 재미로 만든다.

## 3. 단계별 계획

### P1. 상대 존재감 — 접속 상태와 행동 표시

**목표:** 상대가 지금 무엇을 하는지, 연결돼 있는지 항상 알 수 있다.

- 좌석 heartbeat
  - `POST /api/baseball-game/rooms/[code]/heartbeat` 추가. 좌석 쿠키 검증 후 `baseball_game_seats.last_seen_at` 갱신, 탭 가시성(`visible | hidden`)을 함께 저장.
  - 클라이언트는 기존 폴링 루프와 별도로 일정 주기 heartbeat 전송. 주기와 판정 임계값은 `lib/baseball-game/multiplayer/presence.ts`의 명명 상수로 정의.
- 존재 상태 판정 `getSeatPresence(lastSeenAt, visibility, now)` → `"online" | "away" | "offline"`
  - `online`: 최근 heartbeat + 탭 활성
  - `away`: 최근 heartbeat + 탭 숨김
  - `offline`: heartbeat 끊김
- 스냅샷 확장: `opponentConnected: boolean` → `opponent: { presence, lastSeenAgoMs }`
- 상대 행동 문구 `describeOpponentActivity(view, actionOwner)` — 순수 함수, 공개 정보만 사용
  - `awaiting_pitch` → "상대 투수가 사인을 고르는 중"
  - `awaiting_swing` → "상대 타자가 노림수를 정하는 중"
  - `awaiting_card` → "상대 수비가 카드를 검토 중 · 타구 직후" (`cardWindow.timing` 반영)
  - `offline` 우선 → "상대 연결 끊김 · 재접속 대기"
- 재접속 유예 배너: 상대가 `offline`이면 경과 시간 표시, 내가 재접속하면 "경기에 복귀했습니다" 토스트

**수용 기준**

- 상대 탭을 닫으면 임계 시간 안에 `offline`, 탭을 숨기면 `away`로 바뀐다.
- 대기 문구가 단계·카드 타이밍별로 다르게 표시된다.
- heartbeat 응답과 스냅샷에 상대 손패나 비공개 선택이 포함되지 않는다.

**테스트:** `presence.ts` 단위 테스트(경계 시간), service 테스트(heartbeat 좌석 검증·타 좌석 토큰 거부), 컴포넌트 테스트(상태별 문구), E2E(상대 페이지 종료 → offline 표시)

### P2. 샷클락 — 여유 있는 결정 제한시간

**목표:** 경기가 이탈로 멈추지 않게 하되, 충분히 고민할 시간을 준다. 압박은 마지막 구간에만 둔다.

- 저장: `baseball_games.decision_deadline_at timestamptz null` 컬럼 추가(마이그레이션). `GameState`에는 넣지 않는다.
- 기한 설정: 행동이 커밋될 때마다 새 단계 기준으로 서버가 계산.
  - `deadline = now + getPresentationDuration(newEvents) + DECISION_LIMIT_MS[phase]`
  - 연출 시간을 서버가 결정적으로 더하므로 장면 재생 중에는 시계가 줄지 않는다.
  - `DECISION_LIMIT_MS`는 `multiplayer/shot-clock.ts`의 단계별 명명 상수(투구·스윙·카드). 기본값은 §5.
- 여유 장치
  - **작전 타임:** 팀당 경기 중 정해진 횟수만큼 현재 결정에 시간을 추가로 붙인다. 상대 화면에 "작전 타임" 표시와 효과음.
  - **재접속 유예:** 차례인 쪽이 `offline`이 되면 해당 결정 기한을 한 번 연장한다. 그 뒤에도 돌아오지 않으면 자동 행동.
  - **경고는 막판에만:** 남은 시간이 경고 임계값 이하일 때만 시계가 강조되고 틱 소리가 난다. 그전에는 조용한 진행 표시만.
- 만료 처리(지연 평가): `view`·`heartbeat`·`actions` 요청 시 기한이 지났으면 서버가 자동 행동을 커밋.
  - 멱등 키는 `timeout:<revision>`으로 고정해 양쪽 기기가 동시에 감지해도 한 번만 반영.
  - 자동 행동: 투구 → 서버 난수로 스트라이크/볼 선택(고정값이면 상대가 악용 가능), 스윙 → 지켜보기, 카드 → 패스.
  - 행동 로그 `actor_team`은 원래 차례 팀, 이벤트 요약에 "시간 초과" 표기.
- 연속 시간 초과: 같은 팀 연속 N회 시 몰수 처리 여부는 **결정 필요(§5)**.
- UI
  - 내 차례: `BaseballDuelControl`과 카드 결정부에 원형 카운트다운. 경고 구간에서 맥동.
  - 상대 차례: 상대 시계도 표시 — 상대가 오래 고민하는 것 자체가 읽을거리가 된다.
  - 서버 시각과 클라이언트 시각 차이는 스냅샷의 `serverNow`로 보정.

**수용 기준**

- 연출 재생 중에는 남은 시간이 줄지 않는다.
- 작전 타임은 팀별 남은 횟수 안에서만 사용되고, 사용 즉시 양쪽 화면의 기한이 같이 늘어난다.
- 차례인 쪽이 끊기면 기한이 한 번만 연장된다.
- 기한이 지나면 어느 기기에서 먼저 조회하든 자동 행동이 정확히 한 번 반영된다.

**테스트:** 기한 계산 단위 테스트(연출 시간 가산·작전 타임·재접속 유예), service 테스트(만료 전 무변화·만료 후 1회 반영·동시 감지 중복 방지·작전 타임 횟수 초과 거부), E2E(한쪽 무입력 → 자동 진행)

### P3. 사운드스케이프 — 소리로 만드는 경기장

**목표:** 화면을 보지 않아도 경기 흐름과 긴장이 느껴지고, 소리가 결과를 먼저 알려주지 않는다.

기존 원칙(`RULES.md` `rts-scenes-v1`)대로 모든 소리는 Web Audio로 합성하며 녹음 음성·외부 음원은 사용하지 않는다.

**0) 선행 수정 — 장면 동기화**

- 현재 `BaseballAudio`는 revision이 도착하는 즉시 결과음을 몰아서 재생한다. 장면이 "플레이 진행 중"으로 결과를 가리는 동안 홈런·아웃 소리가 먼저 나는 셈이다.
- 효과음 트리거를 이벤트 도착에서 **장면 beat 재생 시점**으로 옮긴다. `usePresentation`이 beat를 진행할 때 해당 beat의 소리를 낸다.
- 매핑은 순수 함수 `getBeatAudio(beat): SoundCue[]`로 분리해 `presentation.ts` 옆에 둔다.

**1) 레이어 구성**

| 레이어        | 내용                                                                                                                                                  | 트리거                                      |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 관중 앰비언스 | 필터링한 노이즈로 만든 상시 웅성거림. 긴장도에 따라 볼륨·밝기 변화                                                                                    | 경기 상태(긴장도)                           |

| 샷클락        | 경고 구간에서만 부드러운 틱, 마지막 몇 초 빨라짐                                                                                                      | 남은 시간                                   |

**2) 내 시점 반응**

- 같은 플레이라도 기기마다 응원석이 다르게 반응한다. 내 팀이 득점하면 환호, 실점하면 상대 응원석의 짧은 환호와 내 응원석의 탄식.
- 판정은 `perspectiveOf(event, seat)` 순수 함수로 내 팀 기준 `good | bad | neutral`을 계산.

**3) 긴장도 모델**

- `getLeverage(view): 0..1` 순수 함수. 이닝(후반 가중), 점수 차, 주자 상황, 아웃, 카운트로 계산.
- 앰비언스 볼륨, 심장 박동 템포, 승부처 배너(P5)가 같은 값을 공유한다. 양쪽 기기에서 동일한 값.

**4) 믹싱과 설정**

- 마스터 → 버스 3개(효과음·관중·음악/시그니처) 구조. 효과음이 날 때 관중 버스를 잠시 낮춘다(덕킹).
- 설정 패널: 마스터 볼륨과 버스별 볼륨, 전체 음소거. 기존 `bbg-broadcast-sound-v1`·`bbg-broadcast-volume-v1` 키는 마스터 값으로 이어받는다.
- 브라우저 자동재생 정책 때문에 첫 탭/키 입력 전에는 소리를 내지 않는다(현재 unlock 방식 유지). 탭이 숨겨지면 앰비언스를 멈춘다.
- 모바일: 개인 기기 모드의 진동(`navigator.vibrate`)을 결과별 패턴으로 세분화(타격, 득점, 아웃, 내 차례 시작).

**5) 구조**

- `lib/baseball-game/audio/` — 순수 매핑: `getBeatAudio`, `getLeverage`, `perspectiveOf`, `getSignatureCue`. 모두 단위 테스트 대상.
- `components/baseball-game/audio/` — `AudioContext` 그래프, 신스 패치(노이즈·오실레이터·엔벨로프), 레이어 컨트롤러. 기존 `BaseballAudio`를 대체.
- 싱글·멀티·파티 공용 화면이 같은 사운드 엔진을 사용한다.

**수용 기준**

- 결과 효과음은 해당 beat가 화면에 나타날 때만 재생되고, 결과를 가리는 동안에는 나지 않는다.
- 같은 이벤트 로그를 받은 두 기기에서 같은 시점에 같은 효과음이 나고, 관중 반응만 각자 시점에 맞게 다르다.
- 버스별 볼륨과 음소거가 저장·복원되며 기존 설정 키를 이어받는다.
- 소리를 꺼도 게임 진행과 화면 연출은 동일하다.

**테스트:** 매핑 순수 함수 단위 테스트(beat별 소리, 시점별 반응, 긴장도 경계), 결과 가림 중 무음 회귀 테스트, 설정 저장·마이그레이션 컴포넌트 테스트. 음색 자체는 직접 들어보며 조정.

### P4. 카드 카운팅 — 공개 정보로 읽는 심리전

**목표:** 상대의 카드 창 열림·패스·사용 기록과 덱 구성을 근거로 상대 손패를 추리할 수 있다.

- 공개 신호 기록 (UI: "상대 카드 노트" 패널)
  - 카드 창이 상대에게 열림 → "상대에게 이 시점에 낼 수 있는 카드가 있었다"
  - 이후 패스(`card_pass`) → "있었지만 아꼈다", 사용(`card_play`) → 해당 카드 공개
  - 이벤트 로그와 `cardWindow`에서 파생. 엔진 변경 없음.
- 덱 트래커
  - 역할별 덱 구성(`CARD_DECK_COUNTS`) 대비 현재 셔플 이후 공개 사용된 카드 수 → 카드별 "최대 잔여 수" 표시.
  - 공수교대 시 손패가 비공개로 버림 더미에 들어가므로(`resetHandsForHalfInning`) 정확한 수가 아니라 상한임을 명시한다. 버림 더미 내용은 노출하지 않는다.
- 엔진 변경(최소): 덱 재셔플 시점을 알 수 있도록 `CardZone`에 `reshuffleCount` 추가, `CardZoneView`로 공개.
  - `schemaVersion` 7 → 8, 저장된 진행 중 경기 상태 마이그레이션 함수 필요.
- 투타 성향 기록: 현재 경기에서 상대의 카운트별 투구(스트라이크/볼)·스윙 선택 비율. 판정 후 공개된 정보만 사용.

**수용 기준**

- 노트와 트래커가 공개된 이벤트만으로 계산되며, 같은 이벤트 로그에서 양쪽 기기에 같은 결과를 낸다(자기 기록은 상대 시점 기준으로 보이도록 별도 탭).
- 버림 더미의 비공개 카드가 응답에 포함되지 않는다.

**테스트:** 파생 함수 단위 테스트(창 열림→패스, 재셔플 경계, 공수교대 상한), 정보 은닉 회귀 테스트(`getGameView` 응답에 버림 더미 내용 없음)

### P5. 상호작용과 공동 연출

**목표:** 같은 경기를 함께 치르고 있다는 감각.

- 리액션 이모트: 정해진 6~8종(예: 박수, 도발, 탄식, 경례)만 전송. 자유 채팅은 제외해 신고·필터링 부담 제거.
  - 저장: 방 단위 최근 리액션(짧은 보존). 폴링 스냅샷의 `recentReactions`로 전달. 좌석당 전송 빈도 제한.
  - 표시: 상대 리액션이 내 경기장 상대 진영 쪽에 말풍선으로 떠오르고, P3의 리액션별 효과음이 함께 난다.
- 승부처 연출: P3의 `getLeverage`가 임계값을 넘으면 양쪽 화면에 동시 배너. 사운드의 긴장 레이어와 같은 값을 사용.

**수용 기준:** 리액션은 상대 화면에 다음 동기화 주기 안에 표시되고 빈도 제한을 넘으면 거부된다. 승부처 판정은 양쪽 기기에서 동일하다.

### P6. 경기 전후 흐름

- 로비: 양 팀 닉네임·팀명 입력, 준비 완료 버튼 후 시작. 참가 QR 표시(`qrcode` 의존성 재사용).
- 재대결: 경기 종료 후 같은 방에서 새 경기, 홈/원정 교대. 양쪽 동의 시 시작.
- 시리즈: 3판 2선승 옵션과 시리즈 스코어 표시.
- 경기 요약: 승부처·득점 장면 하이라이트 재생. 엔진이 결정적이므로 저장된 이벤트로 기존 장면 재생기와 사운드를 그대로 재사용.

### P7. 실시간 알림 전환

기존 계획대로 폴링을 Supabase 비공개 Broadcast의 `{ revision }` 알림으로 교체한다. P5 리액션과 상대 신호음의 체감 지연을 줄이는 것이 주된 이유이며, 실패 시 현재 폴링으로 자동 대체한다.

## 4. 권장 순서

1. **P1 + P2** — 멀티플레이가 멈추는 문제를 해결하고 긴장감의 기반을 만든다. 서로 의존(재접속 유예)하므로 함께 진행.
2. **P3** — 사운드. 결과를 미리 알려주는 기존 문제(0번)를 먼저 고친 뒤 레이어를 쌓는다. 싱글·파티에도 바로 효과가 있다. P1·P2와 파일이 거의 겹치지 않아 병행 가능.
3. **P4** — 카드 카운팅. 엔진 스키마 변경이 있어 별도 단계로 분리.
4. **P5** — 체감 몰입도 상승 폭이 크고 위험이 낮음. P3의 긴장도·효과음을 재사용.
5. **P6 → P7** — 재방문과 반복 플레이 동기.

각 단계는 독립적으로 테스트를 통과한 상태로 커밋한다.

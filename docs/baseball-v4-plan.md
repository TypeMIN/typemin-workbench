## A. 페이즈 분리와 투타 동시 선택 — 규칙 `pitch-duel-v4`

### 결정 사항 (2026-10-13)

- **카드는 지금처럼 순서대로 선언한다.** 뒤 순서가 앞 순서의 카드를 보고 결정하는 정보 구조를 유지한다. 응답 카드 창도 그대로 둔다.
- **투수와 타자의 선택만 동시에 한다.** 한 투구를 "카드 페이즈 → 투타 페이즈"로 나누고, 투타 페이즈에서는 두 사람이 서로의 선택을 기다리지 않고 동시에 고른다.

### 현상

- 투구 1회의 진행: 카드 창(있으면, 순서대로) → 투수 선택 → **투수 잠금 장면 1.25초** → 타자 선택 → 판정.
- 투수가 고를 때 타자는 아무것도 할 수 없고, 투수 잠금이 서버에 반영되고 상대 기기가 알아챈 뒤 장면이 끝나야 타자가 고를 수 있다. 투구마다 왕복 1회와 장면 1개가 더 든다.

### 페이즈 구조

```text
[카드 페이즈]  기존 규칙 그대로
  priorityOrder 순서로 한 역할씩 선언 → 필요하면 응답 창 → 해석
  (낼 카드가 없으면 지금처럼 건너뜀)
        ↓
[투타 페이즈]  신규 awaiting_duel
  투수: 스트라이크/볼 ─┐
                       ├─ 순서 무관, 서로 비공개. 둘 다 모이면 즉시 판정
  타자: 스윙/지켜보기 ─┘
        ↓
[판정 후 카드 페이즈]  after_pitch / after_contact / after_batting / after_hit
  기존 규칙 그대로
```

### 설계

1. **투타 동시 선택**
   - `awaiting_pitch`와 `awaiting_swing`을 새 페이즈 `awaiting_duel` 하나로 합친다.
   - `pitchDuel`에 `pitcherChoice`와 `batterDecision`을 각각 비공개로 저장하고, 두 선택이 모두 모이면 같은 transition 안에서 판정한다.
   - `SELECT_PITCH`·`SELECT_SWING`은 순서와 관계없이 받는다. 이미 선택한 쪽이 다시 보내면 `ALREADY_LOCKED`로 거부한다(번복 금지).
   - 실제 투구 위치는 지금처럼 투수 선택 시점에 상태 RNG로 정한다. 어느 쪽이 먼저 제출하든 RNG를 쓰는 순서가 같도록, 판정 시점에 투구 위치 → 판정 순서로 한 번에 계산한다.
   - 투수 잠금 장면(`pitch_commit` 단독 revision)이 사라져 투구당 장면이 하나로 줄어든다. 대신 선택한 쪽에는 "선택 완료 · 상대 대기"를, 상대에게는 "상대 선택 완료"만 보여 준다.
   - 히트 앤드 런(`HNR`)이 걸려 있으면 타자 선택은 자동으로 스윙이므로 투수 선택만 받는다(현재 규칙과 같음).
2. **카드 페이즈는 현행 유지**: `openCardWindow`·`seekPlayablePriority`·응답 창 로직은 바꾸지 않는다. 카드 페이즈가 끝나야 투타 페이즈가 열린다. 카드 효과(도루, 견제 등)가 투구 전 상황을 바꾸기 때문이다.
3. **행동 주체 API 변경**
   - `getActionOwner(state): TeamSide | null`를 `getPendingOwners(state): TeamSide[]`로 바꾼다. 투타 페이즈에서는 아직 고르지 않은 쪽 전부, 카드 페이즈에서는 지금처럼 한 팀이다. 기존 함수는 호환용으로 남긴다.
   - `isYourTurn`은 "내 제출이 필요하고 아직 하지 않았음"을 뜻하도록 바꾸고, 스냅샷에 `opponentLocked: boolean`을 추가한다. 상대가 골랐는지만 공개하고 무엇을 골랐는지는 공개하지 않는다.
4. **샷클락**: 투타 페이즈는 기한 하나를 두 사람이 함께 쓴다. 만료되면 아직 고르지 않은 쪽만 자동으로 채운다(투구는 서버 난수, 스윙은 지켜보기). 연속 시간 초과는 팀별로 센다. 카드 페이즈 기한은 지금과 같다.
5. **AI(싱글)**: 투타 페이즈가 시작되면 AI는 사람의 선택을 기다리지 않고 바로 자기 선택을 제출한다. 사람 쪽 화면에는 "상대 선택 완료"가 즉시 뜬다.
6. **파티**: 투타 페이즈에서 타석의 타자와 마운드의 투수 개인 기기가 동시에 활성화된다.

### 선택 사항

- **자동 패스 토글:** "이번 타석 카드 안 씀"을 켜면 그 타석 동안 내 카드 창을 서버가 바로 패스합니다. 대기를 줄이지만, 패스가 즉시 끝나기 때문에 상대가 "고민 없이 넘겼다"는 것을 알아챌 수 있습니다. 지금 정보 구조를 그대로 두기로 했으므로 **기본값은 넣지 않음**으로 두고, 필요할 때 다시 논의합니다.

### 변경 범위

- `lib/baseball-game/engine.ts`, `types.ts`(`GamePhase`에 `awaiting_duel`, `PitchDuelState`의 두 선택을 각각 nullable로), `ai.ts`, `duel.ts`, `presentation.ts`(투수 잠금 장면 제거)
- `lib/baseball-game/multiplayer/service.ts`(동시 제출, 소유자 검사), `shot-clock.ts`(부분 자동 채움)
- `lib/baseball-game/party/service.ts`(활성 선수 2명 동시 행동)
- `components/baseball-game/baseball-duel-control.tsx`(투수·타자 버튼을 같은 페이즈에, 상대 선택 완료 표시), 방·파티·싱글 화면
- 규칙 버전 `pitch-duel-v4`, `schemaVersion` 7→8. 진행 중인 v3 경기는 v3 규칙으로 끝까지 진행하고, 새 경기부터 v4를 쓴다(엔진이 `rulesetVersion`으로 분기).

### 수용 기준

- 카드 창이 없는 투구는 투수와 타자의 동시 제출 한 번으로 판정되고, 투수 잠금 장면이 없다.
- 어느 쪽이 먼저 제출해도 같은 RNG 상태와 같은 선택이면 같은 결과가 나온다.
- 상대 선택 내용은 판정 전까지 어떤 응답에도 포함되지 않고, `opponentLocked`만 공개된다.
- 카드 페이즈의 순서, 응답 창, 카드 노트 기록은 v3와 같다.
- v3로 저장된 진행 중 경기를 불러와도 깨지지 않는다.

### 테스트

- 엔진: 제출 순서 교환 불변식(투수 먼저/타자 먼저 결과 동일), HNR 자동 스윙, 카드 페이즈 회귀(기존 엔진 테스트 전부 통과)
- 서비스: 같은 revision에 양쪽이 동시에 제출해도 둘 다 반영(B3의 선택 병합), 번복 거부, 한쪽만 시간 초과
- 정보 은닉 회귀: 판정 전 스냅샷에 상대 선택 없음

## B. 통신 대기 단축

### 현상 (2026-10-13 운영 실측)

- DB 조회 1회짜리 `/api/baseball-game/rooms/ZZZZZZ/public-view` 응답: **0.50~1.02초**, 콜드 스타트 시 2.5초
- 응답 헤더 `x-vercel-id: icn1::iad1::…` → 엣지는 서울, **함수는 미국 동부 `iad1`에서 실행**
- 같은 Supabase REST를 로컬에서 직접 호출하면 0.055초
- `/view` 1회에 DB 2~3회, `/actions` 1회에 4회 이상 왕복(getRoom, getSeatContext, idempotency, commit). 왕복마다 태평양을 건넌다.

### 설계

1. **B1. 함수 리전을 서울로**: `vercel.json`에 `"regions": ["icn1"]`를 지정한다. Next 16에서는 라우트별 `preferredRegion`이 deprecated라 프로젝트 단위로 설정한다. Workbench의 다른 앱도 같은 서울 Supabase를 쓰므로 함께 빨라진다. 예상: 요청당 0.5–1초에서 0.1–0.2초.
2. **B2. DB 왕복 통합**
   - `baseball_room_view(p_room_code, p_token_hash, p_visibility)` RPC 하나로 방, 좌석 판별, 상대 접속 상태, heartbeat 갱신을 처리한다. `/view` 폴링이 heartbeat를 겸하므로 별도 heartbeat 요청은 백그라운드 탭용으로만 남긴다.
   - `/actions`는 방 조회(1회)와 커밋 RPC(1회) 2회로 줄인다. 중복 키 확인은 커밋 RPC가 이미 처리한다.
3. **B3. 동시 제출 병합**: A의 투타 동시 선택은 같은 revision에 양쪽 제출이 몰린다. 지금의 낙관적 잠금(revision 일치)이면 늦게 온 쪽이 409를 받는다. 해결: 선택 제출은 커밋하지 않고 `baseball_games.pending_choices jsonb`에 원자적으로 병합한다(`for update`). 마지막 제출이 도착한 요청이 transition을 실행해 커밋한다. 409 재시도 루프가 사라진다.
4. **B4. 실시간 알림(이전 P7 재설계)** — 결정: 추천안 채택
   - 쉽게 말하면: 지금은 각 기기가 0.25~0.55초마다 서버에 "바뀐 거 있어?"라고 묻는다. 실시간 알림을 쓰면 서버가 변화가 생긴 순간 "바뀌었어"라고 먼저 알려 주고, 기기는 그때만 조회한다. 알림에는 "몇 번째 변경인지" 숫자만 담고 손패나 선택 같은 내용은 담지 않아서, 누가 알림을 엿봐도 얻을 정보가 없다.
   - 막혔던 이유는 비공개 채널 인가에 Supabase Auth JWT가 필요하다는 점이었다.
   - 해결: **알림 내용에 비밀 정보를 넣지 않는다**. 서버가 커밋 직후 Realtime REST 브로드캐스트(`POST /realtime/v1/api/broadcast`, 서버 전용 키)로 `{ revision, roomRevision }`만 보낸다.
   - 채널 이름은 `bbg:` + HMAC(방 ID, 서버 비밀)로 정해 추측할 수 없게 한다. 클라이언트는 공개 키로 구독하고, 알림을 받으면 자기 권한으로 `/view`를 즉시 다시 조회한다. 손패와 RNG는 여전히 `getGameView`를 통해서만 전달된다.
   - 실시간 연결이 정상이면 폴링을 3초로 늦추고, 끊기면 지금의 250/550ms로 되돌린다.
   - 확인 필요: 프로젝트 Realtime 설정에서 공개 채널 브로드캐스트가 허용돼 있어야 한다.
5. **B5. 즉시 반응 UI**: 내 선택은 서버 응답 전에 "선택 완료" 잠금 상태로 즉시 바꾼다. 결과는 서버 판정 뒤에만 보인다. 실패하면 되돌리고 알린다.
6. **B6. 지연 지표**: 클라이언트가 커밋부터 상대 화면 반영까지 걸린 시간(서버 `revisionStartedAt`과 수신 시각의 차이)을 표본으로 수집하고, 개발 모드에서는 화면 구석에 표시한다.

### 수용 기준

- 서울 기준 `/view` p50 200ms 이하, `/actions` p50 300ms 이하(운영 실측)
- 상대가 커밋한 뒤 내 화면 반영까지 p50 400ms 이하(실시간 알림 정상 시)
- 동시 제출 시 409가 발생하지 않는다

### 테스트

- PGlite로 RPC 검증(기존 방식): `baseball_room_view` 좌석 판별, 선택 병합 원자성
- E2E: 두 기기가 동시에 선택을 보내도 한 번에 판정, 실시간 끊김 시 폴링으로 복귀
- 배포 후 `curl -w %{time_starttransfer}`로 응답 시간 재측정

| 스트라이크존 투구 표시 (`PitchMarkers`, `PitchSequence`) | 공이 날아가는 중에 이번 공의 위치와 판정(S/B/IN)이 먼저 표시됨                |
| 행동 알림 (`revisionSummary`)                            | 내가 선택하자마자 "반영 완료 · 홈런" 같은 결과 요약이 뜸(멀티·파티 개인 기기) |
| 결정 패널                                                | 다음 단계("컨택 직후 카드 창")가 보여 컨택 여부가 드러남                      |
| 손패·카드 창                                             | 카드 사용 결과와 새 손패가 먼저 보임                                          |
| 라인스코어·상대 분석                                     | 득점·안타와 공개 성향이 먼저 갱신됨                                           |
| 파티 개인 기기                                           | 연출이 없어 결과가 공용 화면보다 먼저 보임                                    |

### 설계

1. **`useStagedSnapshot(snapshot)` 훅**
   - 화면은 "마지막으로 연출이 끝난 revision의 스냅샷"(staged)과 "최신 스냅샷"(latest)을 따로 가진다.
   - 경기장(`BaseballStadium`)만 latest의 이벤트로 새 장면을 재생하고, 스코어버그·패널·손패·라인스코어·분석·알림·접근성 문구는 모두 staged를 렌더링한다.
   - 경기장이 `onPresentedRevision(revision)`을 알리면 staged를 그 revision의 스냅샷으로 넘긴다. 중간 revision이 폴링으로 건너뛰어졌다면 latest로 바로 맞춘다.
2. **투구 표시 게이트**: `PitchMarkers`·`PitchSequence`는 현재 장면에서 `pitch` beat가 끝난 뒤에만 이번 공을 표시한다. 경기장 내부에서 beat 인덱스로 판단한다.
3. **행동 알림 문구**: 성공 알림은 "선택 완료"까지만 말하고 결과 요약은 넣지 않는다. 결과는 장면과 하단 자막이 전달한다.
4. **결정 패널과 선택 도크**: 연출 중에는 이미 숨기고 있다. staged 기준으로 전환되므로 다음 단계가 미리 보이지 않는다.
5. **스크린 리더**: `aria-live` 영역도 staged 기준으로 읽는다. 장면이 끝난 뒤 결과를 한 번만 읽는다.
6. **샷클락과의 관계**: 서버 기한은 이미 연출 시간을 더해 계산하므로 staged 전환 시점과 시계 시작 시점이 맞는다.
7. **재접속·탭 복귀**: 쌓인 장면이 2개를 넘으면 마지막 장면만 재생하고 나머지는 하단 자막 티커로 요약한다(E3와 같은 규칙).

### 변경 범위

- `components/baseball-game/use-staged-snapshot.ts` 신규
- `BaseballStadium`(`baseball-game-debug.tsx`): `onPresentedRevision`, 투구 표시 게이트
- 멀티 방, 파티 공용·개인 화면, 싱글 화면의 렌더링 소스를 staged로 교체
- `revisionSummary` 알림 제거

### 수용 기준

- 장면이 재생되는 동안 화면 어디에도(접근성 트리 포함) 그 장면의 결과가 나타나지 않는다.
- 장면이 끝나면 200ms 안에 모든 패널이 최신 상태로 바뀐다.

### 테스트

- 컴포넌트: 새 revision 수신 → 연출 중 스코어버그·라인스코어·손패가 이전 값 유지 → 연출 종료 후 갱신
- E2E: 투구 직후 접근성 트리에 판정 문구가 없는지 확인(타임스탬프 기준), 홈런 장면 중 점수가 바뀌지 않는지 확인

## D. 3아웃 장면이 끝날 때까지 이닝 전환 대기

### 현상

- 엔진은 세 번째 아웃 처리, 공수교대(`half_inning` 이벤트), 손패 재분배를 같은 revision에서 끝낸다.
- UI는 즉시 다음 이닝, 빈 베이스, 새 공격팀, 새 손패를 보여 준다. 아웃 장면은 그 위에서 재생된다.

### 설계

1. C의 staged view로 장면이 끝날 때까지 이전 이닝 상태를 유지한다.
2. **공수교대 장면 추가**
   - `buildPresentationCues`가 `half_inning` 이벤트에 전용 cue `inning_break`를 만든다.
   - 스코어보드 카메라로 2.2초 동안 "3아웃 · 공수교대", 이번 이닝 득점과 안타 요약, 다음 이닝 표시를 보여 준다. 오르간 사운드는 이 beat에서 재생한다.
   - 마지막 회 종료(`game_end`)도 같은 방식으로 "경기 종료" 장면을 만든다.
3. **서버 기한**: 공수교대 장면 시간은 `getPresentationDuration`에 포함되므로 샷클락과 파티 게이트가 자동으로 기다린다.
4. **이벤트 정합성**: `half_inning` 이벤트는 이미 새 이닝 값을 담고 있으므로, 장면이 쓰는 아웃 직전 상태(이전 이닝, 이전 공격팀)는 직전 이벤트에서 가져온다.

### 수용 기준

- 세 번째 아웃 장면 → 공수교대 장면 → 다음 이닝 화면 순서로만 보인다.
- 끝내기·콜드(마지막 말 생략) 경우도 같은 순서를 지킨다.

### 테스트

- 프레젠테이션 단위: 3아웃 revision의 마지막 beat가 `inning_break`인지, 소요 시간 포함 여부
- 컴포넌트: 장면 중 스코어버그 이닝 표시가 이전 이닝으로 유지되는지

## E. 파티플레이 진행 밀림 방지

### 현상

- 개인 기기(`baseball-party-player.tsx`)에는 연출이 없어서, 판정이 나오는 즉시 `canAct`가 되어 다음 선택을 보낼 수 있다.
- 공용 화면은 revision마다 장면을 차례로 재생하므로 개인 기기보다 계속 뒤처진다. 사용자가 말한 "플레이 밀림"의 원인이다.
- 서버(`submitPartyAction`)에도 연출 대기 개념이 없다. 파티 커밋 RPC는 `revision_started_at`을 갱신하지 않는다.

### 설계

1. **서버 연출 게이트**
   - 파티 커밋 RPC가 `revision_started_at = now()`를 기록한다(컬럼은 이미 있음).
   - 서버는 `presentationReadyAt = revisionStartedAt + 장면 시간 + 동기화 여유` 이전의 행동을 `PRESENTATION_IN_PROGRESS`(425)로 거부한다.
   - 스냅샷에 `presentationReadyAt`과 `serverNow`를 넣는다.
2. **개인 기기 대기 UI**: 게이트가 닫혀 있는 동안 "경기장 화면을 보세요" 상태와 남은 시간을 보여 준다. 결과는 게이트가 열린 뒤에 공개한다(C와 같은 원칙을 서버 시각으로 적용).
3. **공용 화면 따라잡기**: 네트워크 지연이나 탭 비활성으로 장면이 2개 이상 쌓이면 이전 장면은 1.5배속으로 압축하거나 요약 티커로 넘기고, 최신 장면만 정속으로 재생한다. 늦어도 3초 안에 따라잡는다.
4. **파티 샷클락**: 멀티플레이의 샷클락(연출 가산, 시간 초과 자동 진행)을 파티에도 적용한다. 지금은 방장이 수동으로 넘기는 방법뿐이다. 시간이 지나면 같은 팀의 다음 선수에게 넘기지 않고 자동 행동으로 진행한다.
5. **A와 연계**: 동시 선택이 되면 타자와 투수 개인 기기가 동시에 고르므로 대기 자체가 절반으로 준다.

### 수용 기준

- 연속 30타석 자동 플레이에서 공용 화면과 서버 revision 차이가 1을 넘는 시간이 3초를 넘지 않는다.
- 개인 기기에서 결과가 공용 화면보다 먼저 보이지 않는다.

### 테스트

- 서비스: 게이트 시간 전 행동 거부, 후 허용, 게이트가 장면 시간에 비례
- E2E(파티): 공용 1대 + 개인 2대로 빠르게 연속 행동해도 공용 화면 장면이 쌓이지 않음

## F. 파티플레이 공용 화면 가독성 · UI 최적화

### 현상

- 공용 화면(`baseball-party-screen.tsx`)은 데스크톱 모니터 크기를 기준으로 했다. 글자와 상태 표시가 작고, 기존 민트 톤 UI 그대로다.
- 누가 지금 결정하는지, 다음 타자가 누구인지, 남은 시간이 얼마인지가 TV 거리에서 읽히지 않는다.

### 설계 (기준: 1920×1080 TV, 시청 거리 2.5m)

1. **타이포 스케일**: 루트 글자 크기를 `clamp(16px, 1.05vw, 28px)`로 화면에 비례시킨다. 본문 최소 24px(1080p 기준), 점수 72px 이상, 대비 7:1 이상.
2. **화면 구성**
   - **상단:** 대형 스코어버그
   - **중앙:** 경기장(화면의 65% 이상)
   - **좌우 레일:** 팀별 라인업(현재 타자와 대기 타자 강조, 수비 담당 표시)
   - **하단:** 결과 자막
3. **지금 결정 중 카드**: "원정 · 민수(타자) 선택 중 / 홈 · 지은(투수) 선택 완료"와 원형 샷클락. 동시 선택(A)에 맞춰 양쪽 상태를 따로 표시한다.
4. **결과 콜아웃**: 홈런·삼진·득점·병살은 전체 화면 배너로 1.2초 동안 보여 준다(C의 staged 이후).
5. **정보 절제**: 공용 화면에서는 플레이 기록 표(`BaseballPlayReceipt`)와 세부 버튼을 숨긴다. 방장 조작은 화면 구석의 접힌 메뉴로 옮긴다.
6. **참가 QR**: 로비에서는 크게, 경기 중에는 구석에 작게 상시 표시한다. 중간 참가는 다음 타석부터 라인업에 들어간다.
7. **소리**: 공용 화면이 경기장 사운드를 맡고, 개인 기기는 진동과 짧은 확인음만 낸다(지금 구조 유지, 개인 기기에 확인음 추가).
8. **개인 기기 UI**: 큰 결정 버튼(높이 64px 이상), 내 역할(타자·투수·대기), 남은 시간, "TV를 보세요" 대기 상태, 다음 내 차례까지 남은 타석 수.
9. **리액션**: 개인 기기에서 보낸 리액션이 공용 화면에 이름과 함께 떠오른다(멀티 리액션 재사용).

### 수용 기준

- 1920×1080과 3840×2160에서 2.5m 거리 기준 모든 핵심 정보(점수, 카운트, 아웃, 주자, 결정 중인 선수, 남은 시간)가 읽힌다.
- 공용 화면에 스크롤이 생기지 않는다(16:9, 16:10, 21:9).

### 테스트

- Playwright 스크린샷: 1920×1080, 2560×1440, 3840×2160 공용 화면
- E2E: 결정 중 카드가 양 팀 상태를 정확히 보여 주는지

## G. 메인 그래픽 고도화

### 현상

- 필드 탑뷰(`bbg-field-overview`)는 평면 녹색 부채꼴에 두꺼운 테두리이고, 수비수가 없으며 주자는 점(`bbg-runner-dot`)이다.
- 포수 시점은 지난 작업에서 개선했지만, 카메라 전환이 화면을 즉시 바꾸는 방식이다.
- 첫 화면(`/baseball-game` 설정·싱글 화면)은 예전 민트 톤 그대로라 멀티 방과 디자인이 다르다.

### 설계

1. **중계 카메라 시점 필드**: 홈 플레이트 뒤 높은 위치에서 내려다보는 3/4 원근 시점으로 다시 그린다.
   - 외야 펜스 패딩, 경고 트랙, 잔디 깎은 무늬, 내야 흙 질감, 베이스와 라인, 파울 폴, 외야 관중석, 조명탑
   - 좌표계: 기존 900×700 viewBox 위에 원근 변환 함수(`projectField(x, y, z)`)를 둔다. 기존 `FIELD_POINTS`·`CATCH_POINTS` 데이터는 그대로 쓰고 그릴 때만 투영한다.
2. **선수 표현**: 수비수 9명 실루엣(포지션별 기본 위치, 타구 방향으로 이동하는 애니메이션), 주자 실루엣(달리기 자세), 타자·포수·심판
3. **공 표현**: 높이를 반영한 그림자와 공 분리, 뜬공의 포물선, 땅볼 바운드, 홈런의 담장 넘김, 속도에 따른 잔상
4. **카메라 연출**
   - 포수 시점에서 필드로 넘어갈 때 0.35초 줌아웃 전환을 넣는다.
   - 필드에서는 공을 따라 `transform`으로 이동·확대한다(최대 1.6배). `prefers-reduced-motion`이면 고정 카메라를 쓴다.
5. **경기장 환경**: 이닝이 진행될수록 하늘을 해 질 녘에서 야간 조명으로 서서히 바꾸고, 전광판에 점수를 반영한다.
6. **첫 화면 재디자인**: 방 화면과 같은 야간 중계 디자인을 쓴다. 모드 선택(AI·멀티·파티)을 큰 카드로 보여 주고, 최근 경기와 방 코드 입력을 넣는다. 싱글 경기 화면도 방 화면의 스코어버그, 하단 자막, 결정 패널 구조로 통일한다.
7. **성능 예산**: SVG 요소 수 상한, 애니메이션은 `transform`·`opacity`만 사용, 저사양 기기에서는 장식 레이어를 줄인다(`navigator.hardwareConcurrency <= 4`, `deviceMemory <= 4`).

### 수용 기준

- 중급 모바일(최근 3년 출시 보급형)에서 장면 재생 중 55fps 이상
- 같은 이벤트 로그에서 모든 기기가 같은 장면을 재생한다(결정성 유지)

### 테스트

- 투영 함수 단위 테스트(베이스 좌표 대칭성, 경계)
- Playwright 스크린샷 비교: 장면별 기준 이미지(포수, 땅볼, 뜬공, 홈런, 주루)
- 성능: Chrome DevTools 성능 추적을 CI 밖에서 수동 기록

| 초광폭   | 3440×1440                              | 3열(분석, 경기장, 결정). 경기장은 16:10 비율 유지           |
| TV·4K    | 3840×2160                              | 파티 공용 화면 기준 비율 스케일(F)                          |

2. **방식**: 화면 폭 미디어쿼리 대신 레이아웃 컨테이너 쿼리(`container-type: size`)로 경기장과 레일이 자기 크기에 반응하게 한다. 글자 크기는 `clamp()` 단계 토큰으로 정의한다.
3. **안전 영역**: `env(safe-area-inset-*)`를 적용하고 `100dvh`를 쓰며, 모바일 주소창 변화에 대응한다.
4. **경기장 비율**: SVG `meet` 레터박스 대신 컨테이너 비율에 맞춰 배경(관중석·하늘)을 넓히고, 필드는 중앙에 유지한다.
5. **CSS 정리**: 방·파티·싱글 공용 토큰 파일과 컴포넌트별 CSS로 나눈다. 더 이상 쓰지 않는 `.bbg-mp-*` 규칙(약 900줄)을 지운다.

- 가로 폰에서 경기장과 결정 버튼이 한 화면에 함께 보임

## I. 사운드 보강

### 현상 (현재 큐 목록 `lib/baseball-game/audio/cues.ts`)

- 있음: 투구 바람, 미트, 정타, 파울, 헛스윙, 바운드, 포구, 송구, 슬라이딩, 아웃(저음), 득점, 잠금, 카드 등급음, 오르간(이닝·끝내기·종료), 틱, 작전 타임, 리액션, 내 차례
- 없음: **심판 콜**(스트라이크, 볼, 파울, 아웃, 삼진, 세이프, 볼넷, 몸에 맞는 공), 타구 품질별 타격음(홈런성 큰 타구, 빗맞은 타구, 번트), 뜬공 포구와 내야 포구 구분, 펜스 맞는 소리, 병살 연속 포구, 도루 시 관중 반응, 삼진 전용 효과

### 설계

1. **심판 콜 레이어(신규 버스 `voice`)** — 결정: 음성 합성·TTS·오픈소스 녹음본을 쓴다
   - **콜 목록(14개):** 플레이볼, 스트라이크, 스트라이크(헛스윙), 삼진 아웃, 볼, 볼넷, 몸에 맞는 공, 파울, 파울볼(2S 이후 짧게), 아웃, 세이프, 홈런, 타임, 게임셋
   - **1순위(권장 기본): 오픈소스 TTS로 미리 만든 고정 음성 파일**
     - Korean을 지원하는 오픈소스 TTS로 14개 콜을 한 번만 생성하고 결과 파일을 저장소에 포함한다. 후보는 MeloTTS(MIT)다. 구현 시 라이선스 원문과 한국어 모델 품질을 확인하고, 비상업 전용 라이선스 모델(예: Coqui XTTS의 CPML)은 쓰지 않는다.
     - 생성 후 후처리: 고역 통과(80Hz), 압축, 짧은 경기장 잔향, 콜별 속도·높낮이 조정(삼진·홈런은 길고 힘 있게, 볼은 짧고 낮게)
     - 형식은 Opus 또는 MP3(합계 약 150KB)로 `public/sounds/umpire/`에 둔다. 웹 오디오(`decodeAudioData`)로 불러와 `voice` 버스로 재생하므로 볼륨, 덕킹, 장면 beat 동기화가 효과음과 같게 동작한다.
     - 장점: 모든 기기에서 같은 목소리, 오프라인 동작, 기기 음성 유무와 무관
   - **2순위(선택 스타일): CC0 오픈소스 녹음본**
     - Freesound 등에서 CC0(저작자 표시 의무 없음) 심판 콜 녹음을 고른다. 대부분 영어("Strike!", "Ball", "You're out!")라 설정에서 "영어 심판" 스타일로 제공한다.
     - CC-BY 자료를 쓰면 크레딧 페이지에 출처를 남긴다. 라이선스가 불분명한 자료는 쓰지 않는다.
   - **3순위(대체): 기기 음성 합성** — 파일을 불러오지 못하면 `speechSynthesis`(ko-KR)로 같은 문구를 읽는다. 한국어 음성이 없는 기기는 4순위로 넘긴다.
   - **4순위(최종 대체): 합성 효과음 콜** — 스트라이크는 짧은 상승 2음과 미트, 아웃은 단호한 저음 2연타, 삼진은 상승 3음과 관중 함성처럼 콜마다 구분되는 소리
   - **설정:** 사운드 패널에 "심판 콜" 볼륨, 끄기, 스타일(한국어 TTS / 영어 녹음) 선택을 추가한다.
   - **규칙 문서 변경:** `RULES.md`의 "녹음 음성·외부 음원 미사용" 원칙을 "라이선스가 확인된 오픈소스 음원과 TTS 생성 음성만 사용"으로 바꾸고, 출처·라이선스·생성 설정을 `docs/third-party-audio.md`에 기록한다.
2. **판정별 매핑**: 공의 판정, 카운트 이벤트, 아웃·세이프 판정 장면에서 구분한다.
   - 지켜본 스트라이크와 헛스윙 스트라이크를 구분한다.
   - 2스트라이크 이후 파울은 콜 없이 타격음만 낸다.
   - 세 번째 스트라이크는 "삼진 아웃!"에 전용 효과와 관중 반응을 더한다.
   - 볼넷은 "볼넷"에 1루로 걸어가는 짧은 오르간을 더한다.
3. **타격음 세분화**: 타구 종류(`batted_ball.face`)에 따라 소리를 고른다.

| 타구                         | 소리                   |
| ---------------------------- | ---------------------- |
| 홈런                         | 길고 밝은 크랙과 잔향  |
| 장타 2·3루타(`D2`/`D3`/`T3`) | 강한 크랙              |
| 단타                         | 기본 크랙              |
| 땅볼                         | 둔탁한 타격음과 바운드 |
| 내야 뜬공(`PO`)              | 빗맞은 소리            |
| 번트·스퀴즈 카드             | 짧은 톡 소리           |

4. **포구음 세분화**: 외야 플라이는 멀리서 들리는 잔향 섞인 포구음, 내야는 근거리 글러브음, 1루 송구 포구는 미트 팝, 병살은 포구·송구·포구를 연속으로 낸다.
5. **상황 사운드**: 펜스 직격음(`D2`/`D3`), 도루 시작 때 관중 웅성거림 상승, 견제구, 실책 때 관중 탄식, 승부처 오르간 "차지" 리프(긴장도 0.75 이상에서 타석 시작 시 1회)
6. **믹싱**: 심판 콜이 나올 때 관중 버스를 낮춘다. 동시 발음 제한(같은 beat 최대 4개)으로 소리가 뭉개지지 않게 한다.
7. **모바일**: iOS는 `touchend`에서 오디오 잠금을 해제한다. 무음 스위치가 켜져 있을 수 있으니 첫 재생 때 "소리가 안 들리면 무음 모드를 확인하세요" 안내를 띄운다.

### 수용 기준

- 모든 투구 판정과 아웃·세이프에 서로 다른 소리(콜)가 난다.
- 콜은 해당 beat가 화면에 나타날 때만 재생된다(C 원칙).

### 테스트

- 매핑 단위 테스트: beat별 콜과 효과음(지켜본·헛스윙 스트라이크, 2S 파울, 삼진, 볼넷, 타구 종류별)
- 음성 합성 대체 경로: `speechSynthesis`가 없을 때 합성 콜로 대체되는지
